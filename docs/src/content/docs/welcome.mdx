Coding agents write faster than you can read. After a week of agents working in parallel, nobody can say with confidence what is implemented, what was only planned, and what quietly broke.

Scryer answers that with evidence. It reads your repository and derives a [C4](https://c4model.com/) model of it: containers from packaging, components from modules, links from imports, and claims from your behaviour tests. Nothing in the model is written by hand or by an agent; it is computed from the repo, so it cannot drift.

## How it works

- **[The claim is the test.](/scryer/concepts/claims/)** A behaviour test's description is an EARS claim about the code it tests: *When a save fails, keeps the draft.*
- **The level is the test level.** An e2e test claims for the system, an integration test for its container, a unit test for its component.
- **[Status is derived.](/scryer/concepts/status/)** A claim is proven when its test is green and nothing it exercises changed since; planned when the test is a todo; stale when the code moved under it; failing when red.
- **[Styles are structural claims.](/scryer/concepts/structure/)** A container declares its architecture style in `.scryer/structure.toml`, and the import graph is checked against it.
- **Planning is writing todo tests.** An agent plans a change by writing the claims it will satisfy as todo tests. You read a column of sentences and watch them flip to proven.

## The C4 hierarchy

| Level | Comes from | Claims from |
|-------|------------|-------------|
| **System** | `structure.toml` | end-to-end tests |
| ↳ **Container** | a package (crate, npm/pnpm workspace package, pyproject, csproj) | integration tests at its boundary |
| &nbsp;&nbsp;↳ **Component** | a module or directory inside it | unit tests |
| &nbsp;&nbsp;&nbsp;&nbsp;↳ **Symbol** | the code's definitions | — |

People and external systems are named in `structure.toml`; links are the import graph.
