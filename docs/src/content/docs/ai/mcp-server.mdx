The MCP (Model Context Protocol) server is what makes scryer a two-way tool. You edit the visual canvas, and AI agents read and modify the same model programmatically.

## How it works

The `scryer-mcp` binary ships bundled with the desktop app. When configured, your AI agent spawns it as a subprocess and communicates over stdio.

Everything the agent does through MCP shows up on your canvas. Author a node through a tool and it appears in the editor; rearrange things in the editor and the agent sees the update on its next read.

## Two layers: the plan and the committed model

Scryer keeps the model in two layers on disk:

- The **committed** model (`.scryer/model.scry`) — the source of truth: what the code is believed to satisfy.
- The **plan** (`.scryer/planned.scry`) — the editable draft you and the canvas author.

Their difference is the **pending** work queue (`get_pending`): model intent not yet reflected in code. A separate axis, **drift** (`get_drift`), tracks the opposite — code that changed out from under the committed model.

You rarely think about layers when calling tools: the editing tools write the plan, the reconcile tools fold or anchor the right layer for you, and reads return the plan by default (so you see your own edits). The one knob is `layer: "committed"` on a read, when you specifically want the source of truth.

## Available tools

An agent picks a tool by asking one question: *am I describing the architecture (**model**), or closing a gap between model and code (**reconcile**)?* The reads serve both.

### Understand

| Tool | What it does |
|------|-------------|
| `read_model` | The model — overview, or one node's subtree. Defaults to the **plan**; pass `layer: "committed"` for the source of truth |
| `search_model` | Fuzzy text search across names, descriptions, technology, and responsibilities |
| `query_model` | Structural query by node shape (kind, empty, responsibility/child counts…) |
| `get_health` | Observability rollup — anchor coverage, drift flags, and darkness (code the model doesn't describe) |
| `validate_model` | Structural validator — parent-kind mismatches, dangling links, coverage gaps |
| `get_pending` | The **model→code** work queue: how the plan diverges from the committed model |
| `get_drift` | The **code→model** divergence: which committed scopes changed on disk since the last reconcile |
| `get_rules` | The binding modeling rules — what earns a symbol, responsibility altitude, when a group is right |
| `read_codebase` | Annotated project tree — deployable units, data stores, manifests, infra configs |

### Model — author the architecture

Typed and self-documenting; each writes the **plan**.

| Tool | What it does |
|------|-------------|
| `add_person` / `add_system` / `add_container` / `add_component` / `add_symbol` | Create a node of each C4 kind — mints ids, validates parentage, anchors symbols to source |
| `update_nodes` | Patch node fields and responsibilities by id |
| `move_nodes` | Re-parent a node and its whole subtree |
| `move_responsibilities` | Move a responsibility from one node to another |
| `add_links` / `update_links` / `delete_links` | Same-level relationships between nodes |
| `add_group` / `update_group` / `delete_group` | Group sibling nodes (a secondary, packaging axis): create / patch / remove |
| `delete_nodes` | Remove a node because its **code** should go away — stages real removal work in the plan |
| `update_source_map` | Anchor responsibilities and nodes to source (file + symbol + line range) |

### Reconcile — keep model and code in agreement

| Tool | What it does |
|------|-------------|
| `mark_implemented` | Fold implemented plan work into the committed model (including folding a deletion once you've removed the code) |
| `descope` | Drop a node from the **model** while leaving its code untouched — relocates its responsibilities to the parent; model-only, no pending work |
| `reconcile_drift` | Accept the current code as the truth and advance the drift anchor, so the same changes stop surfacing |
| `set_drift_watch` | Pause or resume drift detection while you're mid-implementation |

### Generation pipeline

Primitives scryer's own driven sessions use during codebase→model generation and drift checks — **not** for interactive editing (use the typed tools above).

| Tool | What it does |
|------|-------------|
| `fill_container` | Fill a whole container's component + symbol subtree from code in one atomic write |
| `set_model` | Seed the entire model (system node + container skeleton) |
| `set_node` | Write a node's whole subtree at once |
| `set_groups` | Create or replace groups in bulk from raw JSON |
| `flag_drift` | Record the drift-check verdicts (undescribed behaviour → vagrant, regressed claims → stale) into the plan |

## Reading strategies

Agents don't need the whole model at once:

- **`read_model`** with no node returns the small overview (tree down to components, symbols excluded). Pass a node id to drill into that subtree, including its symbols. Oversized subtrees degrade to a child skeleton so the agent can drill further.
- **`search_model`** to locate a concept by text, **`query_model`** to find nodes by shape (e.g. every empty symbol).
- **`get_health`** before reading full subtrees, to decide *where* work is needed.

## The working loop — plan first, then code

The model leads; the code follows. When a change will alter behaviour, capture the intent in the plan **before** writing code:

1. **Consult** the area — `get_health`, then `search_model` / `read_model` for the governing nodes and their responsibilities.
2. **Author the intended change** into the plan with the typed `add_*` / `update_*` tools. It shows up on the canvas as pending plan.
3. **Implement** the code to that plan, then `mark_implemented` to fold it into the committed model.
4. **Reconcile** anything the code does that the plan didn't capture: `get_drift` → examine → `flag_drift` / `reconcile_drift`, or `descope` what shouldn't be modeled.

When building a model from an existing codebase, structure is extracted into the committed model directly (the generation pipeline), and `get_rules` governs every modeling judgment — call it and follow it, then `validate_model` and fix every warning.
